Le cache de build

Modifiez un Dockerfile ou un fichier, reconstruisez, et regardez quelles étapes sont rejouées

À retenir La règle

Chaque étape d’un build a une clé : l’empreinte de la clé de l’étape précédente, de l’instruction, et du contenu des fichiers copiés. Si le cache de build connaît cette clé, la couche est réutilisée (CACHED) ; sinon l’étape est exécutée, et toutes les suivantes avec elle, puisque leur parent a changé. Le cours : Le cache de BuildKit : la clé de chaque étape.

Cet artefact a besoin de JavaScript.

Précaution C’est une simulation : les durées sont fictives et les clés sont des empreintes simplifiées. Les instructions, elles, se modifient librement, et les flèches les déplacent.

À essayer

  1. Construisez deux fois de suite. Que coûte le second build ?
  2. Modifiez le contenu de index.php, puis reconstruisez. Quelles étapes sont rejouées, et pourquoi l’installation des paquets l’est-elle aussi ?
  3. Descendez l’instruction COPY index.php sous le RUN, reconstruisez, puis modifiez de nouveau index.php. Que coûte maintenant une modification du code ?
  4. Remettez dans index.php un contenu que vous avez déjà construit. Le build est-il rejoué ?
  5. Les dépôts Debian ont reçu des mises à jour de sécurité depuis votre dernier build. Votre RUN apt-get update est-il rejoué ? Comment l’obtenir ?
Réponses
  1. Rien : toutes les clés sont connues, tout est CACHED.
  2. Le COPY, parce que le contenu du fichier entre dans sa clé ; puis tout ce qui suit, dont les 38 secondes d’installation, parce que la clé du parent entre dans la clé de chaque étape.
  3. Deux dixièmes de seconde, le temps des deux copies : l’installation des paquets précède désormais le code, sa clé n’en dépend plus. C’est la règle « instructions stables d’abord » : Dockerfile : bonnes pratiques.
  4. Non : le cache garde une couche par clé, pas seulement la dernière. Un contenu déjà construit retrouve sa clé.
  5. Non : l’instruction n’a pas changé, sa clé non plus ; le cache ignore ce que la commande irait chercher sur le réseau. Pour reconstruire sans le cache : docker image build --no-cache --pull.
